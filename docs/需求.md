# 新增需求

## 20260912

1. 一台主机只运行一个实例。
   — **已实现**（原由 `tauri-plugin-single-instance` 提供，2026-09-13 加固：
   第二实例区分是否系统拉起、补齐最小化窗口还原）。
2. 可以设置开机启动。
   — **已实现**（2026-09-13）。拆为两个独立开关：「开机自动启动」（事实源是操作系统，
   经 `cmd_get_autostart` / `cmd_set_autostart` 直读直写，本地不留副本）与
   「启动时最小化到托盘」（`AppSettings.start_minimized`，对手动启动与开机自启同样生效）。
3. 服务端可以设置最大可以传输的文件或者剪贴板内容最大多大，当超出限制时，客户端弹出提示：文件/剪贴板内容太大，无法传输。
   — **已实现**（2026-09-13）。核验发现本条要的限额此前**根本不存在**：服务端只有
   条目数、单帧 payload、全局管道数、控制面消息体积四处限制，没有一处按「单个文件
   大小」或「剪贴板内容大小」计，客户端 `cmd_send_files` 对大小完全不检查。
   本轮是从零建立。这也是首次改动 `server/`。

   新增五项限额，全部由**服务端**环境变量配置，客户端只读（见下「为什么不可写」）：

   | 字段 | 默认 | env |
   | --- | --- | --- |
   | 单个文件 | 128 MB | `UNIDROP_MAX_SINGLE_FILE_BYTES` |
   | 单次总量 | 256 MB | `UNIDROP_MAX_TOTAL_TRANSFER_BYTES` |
   | 剪贴板图片 | 64 MB | `UNIDROP_MAX_CLIPBOARD_IMAGE_BYTES` |
   | 剪贴板文本 | 4 MB | `UNIDROP_MAX_CLIPBOARD_TEXT_BYTES` |
   | 单次文件数 | 64 | `UNIDROP_MAX_ITEMS_PER_OFFER` |
   | 单账号并发 | 8 | `UNIDROP_MAX_CONCURRENT_TRANSFERS` |

   MB 一律按 1024×1024 计，与 `cache_max_size_mb` 的既有约定一致。

   **限额分两层且不得混用**：通用维度（总量、条目数）对所有类型生效；内容维度按
   `data_type` **互斥**——文件走单文件上限，剪贴板图片、文本各走各的。叠加会让
   运营调高的图片上限被单文件上限静默压制，等于新造一个「配了不生效」的旋钮。

   **`0` 的语义与 env 解析的三态**：`0` = 不限制该项；未设置 = 取默认值（不是 0）；
   **非法值（拼错、带单位如 `2GB`、负数）退回默认值并打 warn，不得变成 0**——
   `strconv` 失败返回的正是 0，直接采用会**静默解除限制**而运营以为刚配好了上限。
   启动日志有一行 `transfer limits in effect` 可核对实际生效值。

   **超限改为显式拒绝**。改造前条目数超限只打一条 warn 然后 `continue`，而发送端
   此时已写入待发队列与 `TRANSFERRING` 历史行，于是永久等待一条不会到来的应答，
   直到下次启动被复位。相邻缺陷一并修正：原判定写在 `err == nil` 之内，
   payload 解析失败反而被放行。

   **两条拒绝路径的回送方向相反**：OFFER 的发送方是当前连接；ANSWER 的当前连接是
   接收方、`ToDevice` 才是发送方。复用同一个 helper 会把提示发给错的那一方。

   客户端预检放在**算哈希之前**（大小只需 metadata），且条目计数与 `prepare_offer`
   的跳过口径一致（目录与不可读项都不计），否则选了目录的用户会被误拒。
   服务端未下发限额时（老服务端）沿用客户端自有兜底常量，**既不退化成「无限制」
   也不退化成「全部为 0」**；兜底的文本 4 MB 与服务端默认文本上限数值相同纯属
   巧合，两者是独立常量、不得合并。

   顺带收敛三个死字段（`config.MaxItemsPerOffer`、`config.HeartbeatInterval`、
   `AppSettings.rate_limit_mb`），并把整份不被任何代码读取的
   `configs/config.example.yaml` 换成与实际机制一致的 `.env.example`。

   **三项行为变更**（默认值相对改造前）：单次文件数 1000 → 64；剪贴板图片
   32 → 64 MB（放宽）；单个文件与单次总量由「完全不检查」变为 128 / 256 MB。
   剪贴板文本维持 4 MB 不变。

   **为什么客户端不可写**：原第 6 条曾要求「客户端可以设置服务端的一些参数」，
   论证后发现在当前架构下无法成立（整个部署共用一把 PSK，`account_id` 由客户端
   自报，按字面实现等于任何能连上的客户端都能改写全服务端策略），该条已删除。
   三方案论证存档于 `.reviews/server-transfer-limits/plan/`。

   **限额的执行强度**：服务端校验的是 offer 里客户端**自报**的大小，数据面没有
   逐会话字节核算。因此这组限额是面向诚实客户端的容量与体验约束，
   **不构成对篡改客户端的字节级执行**——与 `account_id` 的定位同级。
4. 可以设置传输历史保存最新的多少条，超出的删除（界面提醒和缓存的内容）。
   — **已实现**（2026-09-13）。新增 `AppSettings.history_max_entries`，默认 100，`0` = 不限制。
   超出的最旧记录连同其数据库行（四张表）与磁盘缓存文件一并删除。
   两条硬约束：进行中的任务不删；文件仍处于 2 小时剪贴板免疫窗口内的会话本轮跳过。
   触发点为任务落终态后、保存设置后、启动时（启动先把崩溃残留的非终态行复位为 FAILED，
   否则死行会永久占住保留额度）。列表**显示**上限与**淘汰**上限解耦，前者是防御性常量。
   — **补充**（2026-09-13，local-store-account-scope）：该上限自本轮起是**每账号**
   语义而非全库总数。两个账号各留 100 条时库内会有 200 条——这是分区的必然结果，
   否则一个账号频繁传输就会把另一个账号的历史挤光。与之相对，缓存的 TTL 与容量
   上限（第 8 条）保持**全局**：磁盘是共享的物理资源，按账号各配一份就是超卖。
   启动复位（`reset_stale_in_flight`）同样保持全局，否则上个账号崩溃留下的死行
   永远无人复位。
5. 可以设置传输任务完成后在界面中保持多久，一段时间后自动在界面中消失。
   — **已实现**（2026-09-13）。新增 `AppSettings.transfer_card_retain_secs`，默认 30 秒，
   `0` = 不自动消失。**只作用于 COMPLETED 卡片**：失败卡片始终保留到手动关闭，
   因为错误 toast 仅 4 秒，卡片再自动消失就没有入口能看到失败原因了。
   仅影响界面卡片，不删历史记录与缓存。
6. 同时支持好多个用户。
   — **已实现**（2026-09-13）。核验发现分发路径其实早就按账号过滤了
   （`ListByAccount` / `BroadcastToAccount` / 信令转发与限额计数全部比对
   AccountID，没有任何一处「广播给所有已连接客户端」），所以功能意义上的
   多用户一直是成立的。本轮修的是「即使各方都守规矩也会互相误伤」的几处：
   **① 身份格式校验**：`account_id` / `device_id` 限定 1–64 字节的 ASCII 子集，
   排在验签**之前**（格式错不烧 nonce，否则重试会漂成「重放攻击」）。
   此前空账号会形成一个所有「忘了填」的客户端共享的公共桶。
   **② 注册表改复合键** `(account, device)`：此前以裸 DeviceID 为键，
   另一个账号用同名 device_id 连上来会直接把你的设备踢下线。
   同账号同设备重连顶号的正当行为保持不变。
   **③ 会话归属保护**：此前 `RemovePipe` 对客户端自报的 session_id
   不做任何校验，任何已鉴权客户端都能零凭据拆掉别人正在传输的管道；
   授权覆盖同样无归属检查。
   **④ 授权失败双向拒绝**：此前非限额类失败会转发一个没有 token 的 ANSWER，
   客户端静默跳过，发送方永久挂起。
   **⑤ 生命周期联动**：授权条目 TTL 5 分钟而管道靠 60 秒空闲存活，
   两者原本互不相干，导致超过 5 分钟的长传输会丢掉授权记录 ——
   结束时被判成未授权拆除，且账号在途计数归零使容量拒绝退化到数据面。
   **凭据模型保持不变**：仍是单把全局 PSK，`account_id` 仍由客户端自报，
   账号仍是便利分区而非安全边界。per-account 凭据与 JWT 未做。
   遗留项**已解决**（2026-09-13，local-store-account-scope）：`transfer_tasks`
   已加 `account_id` 列，历史列表与修剪按账号分区；四个直接读缓存文件的 IPC
   命令（按会话装载 / 按路径装载 / 另存为 / 在文件管理器中显示）加了归属闸门，
   接收完成后的自动装载也会在写剪贴板前复核归属（防传输途中切账号）；切账号时
   广播 `account-changed` 让界面重拉，避免残留卡片被点开。
7. 全程加密。
   — **已实现**（传输层 2026-09-13，内容层 2026-09-14）。传输层：客户端此前**无条件**跳过
   TLS 服务器证书校验（`verify_server_cert` 直接返回成功，控制面与数据面
   都走这条路），意味着即便连 `wss://` 也挡不住中间人。现默认走 webpki 根
   证书校验，跳过校验改为设置项 `allow_insecure_tls`（默认关闭），
   供自签证书 / IP 直连 / 非公共 CA 三类部署显式选择；证书失败会单独提示，
   而不是让用户看着它反复重连。
   **已实机验证**（2026-09-13）：默认档对 self-signed / expired / wrong-host
   （badssl.com）与本地自签四种无效证书全部拒绝，服务端侧可见
   `TLSV1_ALERT_UNKNOWN_CA`；勾选后同一张自签证书握手成功（TLSv1.3）。
   连带发现一个会让人查很久的坑：**自签证书必须是 X.509 v3**，这一条勾选与否
   都绕不过——rustls 在解析阶段就拒绝 v1，早于「是否校验签发者」的判断，
   而 macOS 自带 LibreSSL 的 `openssl req -x509` 默认生成的正是 v1。
   **SAN 是另一个条件，只在走公共 CA 校验时才需要**：它服务于主机名校验，
   另外两档都不查名称。此前这里把两者并列成同一个必要条件，机制上不对。
   已写进 USER_GUIDE。
   **信任模型于 2026-09-14 扩成三档**（tls-trust-modes）。起因是一次实际故障：
   用户用 `wss://<IP>` 连一台证书只签给域名的服务器，rustls 报 `NotValidForName`，
   而当时的提示一律引导去勾「允许不安全连接」——那张证书其实是**完全合法**的
   Let's Encrypt 证书，正确处置只是把地址换成域名。原来的两档设计
   （全信任公共 CA / 全不校验）逼着这类部署在「连不上」和「对所有中间人敞开」
   之间二选一，中间档 `Pinned`（比对证书 SHA-256 指纹，公共 CA 校验不过时才回退）
   就是为它和自签部署补的。同时把证书失败按 rustls 的具体成因分成六档，
   各给各的处置：名称不匹配引导改地址并**明确劝阻**关校验，过期引导续期，
   X.509 v1 直说关校验也无效。横幅原先用 `truncate` 把多行建议压成一行，
   关键信息全被截断，一并修掉。
   **E2EE 已实现**（2026-09-14，e2ee-payload-encryption）。此前占位的协议位
   （`FLAG_ENCRYPTED`、`encrypted`、帧头预留的 12 字节 `Nonce`）全部启用：
   数据块走 AES-256-GCM，会话密钥由 `HKDF-SHA256(psk, salt=session_id,
   info="UNIDROP-E2EE-v1|"+account_id)` 每次传输现派生。
   文件名、内容 sha256 与预览摘要一并加密进 `encrypted_metadata`——
   sha256 尤其要藏，服务端拿它查表就能确认传了哪个已知文件。
   **服务端零改动**：中继不解密、不验 CRC32、限额只读未加密字段。
   实现上有四处承重决定，都写进了代码注释：明文块长取 `4MB - 16`
   （满块密文恰好填满上限，否则会被中继以 `ErrPayloadTooLarge` 断连）；
   CRC32 改算在**密文**上（算明文等于把明文指纹送给中继，短文本可被枚举确认）；
   nonce 由 `(item_index, chunk_index)` 构造并留 4 字节做域分隔，接收端自行重算
   而不信帧头；AEAD 失败按单块 3 次 **与会话累计 3 次**双层熔断（只按单块计数时，
   滑动窗口里 4 个在途块各失败一次永远够不到阈值，会退化成无限重传）。
   能力协商读在线设备表的 `app_version`，在发 OFFER **之前**定形态——
   不能走 ANSWER 回传，服务端会在授权后重建该载荷并丢弃未知字段。
   对端过旧时回落明文并给出可见提示。
   **仍未做**：前向保密（PSK 长期不变）、设备间隔离（单 PSK 即组密钥）、
   防主动降级（协商信息经过服务器，属机会性加密）。
   本地 SQLite 与缓存文件**仍是明文**——主要威胁（设备失窃）已被操作系统全盘
   加密覆盖，独立评估后判定不值得引入 SQLCipher，不是排期不下。
8. 磁盘缓存文件要定时删除。
   — **已实现**（2026-09-13）。核验发现定时清理早已存在（每小时一次，24h TTL +
   10GB LRU），本轮是把写死的策略参数开放为配置项，而非新建第二套清理：
   `cache_ttl_hours`（默认 24，`0` = 不按时间清理）、`cache_max_size_mb`
   （默认 10240，`0` = 不限容量）、`cache_sweep_interval_minutes`（默认 60，最小 1）。
   同时收敛了「常量与 SQL 字面量两套值」的陷阱：`DEFAULT_TTL` 与
   `CLIPBOARD_LOCK_DURATION` 原本是死代码，真正生效的是 SQL 里的裸数字，
   改常量不会有任何效果且无编译警告；现全部集中到 `core/retention.rs`。
   清理循环改为「先 sweep 后 sleep」以保留「启动即扫」；`sweep` 对齐
   `prune_history` 的三段式，磁盘 IO 不持锁。
9.  Bug：在线协同设备的列表中显示的设备运行的版本号跟实际不一致。
    — **已修复**（2026-09-13）。根因是版本号有三份互相独立的字面量：上报给中继
    服务器的、本机信息的、前端标题徽标的，而 Cargo.toml 等早已是 0.1.1。
