## 1. 关于 u32 溢出的独立核算（AGY-02 / GLM-02）

两侧都指出了溢出，但严重程度要自己算才看得清。实算结果：

| 设定值 | 字节数 | 是否溢出 u32 | release 回绕后 |
|---|---|---|---|
| 4095 MB | 4,293,918,720 | 否 | 正常 |
| **4096 MB（4GB）** | 4,294,967,296 | 是 | **0** |
| **8192 MB（8GB）** | 8,589,934,592 | 是 | **0** |
| 10240 MB（默认值） | 10,737,418,240 | 是 | 2,147,483,648（~2GiB） |
| 1048576 MB（§3.5 上限） | 1,099,511,627,776 | 是 | **0** |

两条结论：

- **默认值就会踩中**：10240 MB 回绕成 ~2GiB，低水位随之变成 ~1.7GiB，
  LRU 会大规模删除用户本想保留的缓存——而且是在用户什么都没改的情况下；
- **4GB / 8GB / 1TB 回绕成 0**，恰好落入我自己定义的「`0` = 不限容量」，
  语义 180 度反转。这几个又正是用户最可能填的整数值。

GLM-02 还指出 §4.1 的测试值「上限 100MB → 低水位 80MB」太小（104,857,600 < u32::MAX），
**这个宽度错误在那条测试下照样是绿的**。这一点尤其准确：一条测不出目标缺陷的测试
比没有测试更糟，因为它给人已经覆盖了的错觉。

## 3. 为什么 AGY-04 不引入 Notify

AGY-04 给了两个方向：加通知机制让改动立即生效，或修正测试。我选后者，理由要写清楚，
因为这是**接受意见但不采纳其首选方案**：

用 `select!` 让 sleep 可被唤醒看似简单，但唤醒之后的语义不平凡：

- 唤醒即 sweep？那么用户每保存一次设置就触发一次全量扫描，频繁保存会变成反复扫描；
- 唤醒只重算 sleep？那么「距上次 sweep 已过多久」必须自己记账，否则连续保存设置
  会不断重置计时，sweep 被无限推迟——正是 AGY-01 批评的那类饥饿。

正确实现需要维护「上次 sweep 时刻」并计算剩余时间，逻辑不难但要额外的状态与测试。
而收益仅是「改间隔后不必等一轮」——这是个低频操作（改完通常也不急着看效果），
且重启应用即可立即生效。

**决定**：维持 sleep 不可唤醒，代价通过两处文字兑现——设置项说明写明「下一轮生效，
重启立即生效」，验收步骤补上重启前置。若日后确有需求，落点是 §3.3 的循环体。

## 4. 修订后的计划（仅列相对原稿的变更）

原稿的 §1（现状核验）、§2.1 默认值、§2.3 低水位、§2.4 剪贴板免疫、§2.5 SQL 参数化、
§2.7 serde default 两侧均确认无误，**整体保留**。以下是变更。

### 4.1 §2.6 / §3.3 调度循环改为「先 sweep 后 sleep」（AGY-01 / GLM-01）

```
loop {
    sweep(RetentionPolicy::from_settings(当前设置));   // 启动后立即扫一次
    sleep(effective_sweep_interval(当前设置));          // 每轮重新读设置
}
```

保留了「启动即扫」与「间隔可变」两个性质。改动间隔在下一轮生效——这一点写进
设置项说明与 §4.4 验收步骤（见 §3）。

### 4.2 §3.1 `retention.rs` 增补两个条目（AGY-03 / AGY-05 / GLM-03）

除原有常量外新增：

```rust
/// 有效清理间隔：唯一的钳制入口，保存期与调度期共用，单测直接针对它。
/// 内部 .max(MIN_SWEEP_INTERVAL_MINUTES)，杜绝 Duration::ZERO 让 interval panic。
pub fn effective_sweep_interval(settings: &AppSettings) -> Duration;
```

并在 `core/mod.rs` 补 `pub mod retention;` 与 `pub use retention::*;`（AGY-05）。

### 4.3 §3.2 `RetentionPolicy` 定宽与构造入口（AGY-02 / GLM-02 / GLM-04）

```rust
pub struct RetentionPolicy {
    pub ttl_hours: u32,
    pub max_size_bytes: u64,   // ← 必须 u64
}

impl RetentionPolicy {
    /// 唯一构造入口。MB→字节先升位再乘：(mb as u64) * 1024 * 1024。
    /// 按 u32 相乘的话，默认 10240 MB 就会溢出（debug panic / release 回绕成
    /// ~2GiB），而 4096、8192、1048576 MB 会回绕成 0，落入「0 = 不限容量」
    /// 使语义完全反转。
    pub fn from_settings(s: &AppSettings) -> Self;
}
```

`sweep` 同时改为三段式（GLM-04）：选取（持锁）→ 删文件（不持锁）→ 删行（重新取锁）。

### 4.4 §3.4 `cmd_save_settings` 落库前规范化（AGY-03 / GLM-03）

落库前对 `cache_sweep_interval_minutes` 用 `effective_sweep_interval` 规范化，
使「后端校验」有真实落点。§2.2 措辞相应改为「保存期规范化 + 调度侧兜底」。

### 4.5 §3.5 `parseU32` 的空串文案按 min 分支（AGY-05）

`min > 0` 时空串提示改为「不能为空（最小 {min}）」，不再引导用户填 `0`。

### 4.6 §4 测试计划增补

§4.1 增：

- **大值换算**：10240 MB → 10,737,418,240；1048576 MB → 1,099,511,627,776；
  **4096 MB → 4,294,967,296**（专守「回绕成 0」的语义反转，GLM-02）；
- 删文件段失败时该条目的行保留（GLM-04 的三段式）。

§4.2 增：`effective_sweep_interval` 对 `0`、`1`、正常值的返回（GLM-03，现在可测了）。

§4.4 步骤 2 补前置条件：**保存后重启应用**再观察（AGY-04）。

### 4.7 顺带吸收两条盲区提示

两侧「未覆盖范围」里提到、未列为正式意见但确实要处理的：

- `client/src/App.test.tsx` 的 `baseSettings` 夹具需补三个新字段（编译期会暴露，
  但列入清单免得实现时卡壳）；
- `last_accessed_at` 除 `register_entry` 外**无任何更新路径**，所谓 LRU 实为「注册序」。
  这是既有缺陷，本轮**不修**（超出需求第 9 条范围），但记入 §5，避免日后误以为
  本轮已经处理过 LRU 的正确性。

### 4.8 §5「明确不做」增补

- 不引入 sleep 唤醒机制（理由见 §3）；
- 不修 `last_accessed_at` 不更新导致的「LRU 实为注册序」问题——既有缺陷，
  与本轮的参数可配置化正交，混在一起会让本轮范围失控。
