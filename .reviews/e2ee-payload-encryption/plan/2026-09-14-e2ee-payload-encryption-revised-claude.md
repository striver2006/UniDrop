## 2. 修订内容

### 2.1 协商改为 app_version 前置（对应 AGY-01 / GLM-01 / GLM-02）

原设计「发 OFFER → 等 ANSWER 的 e2ee_ok → 决定加不加密」有两处致命伤：
元数据在发 OFFER 时就已抹空（AGY-01/GLM-02），且 `e2ee_ok` 根本回不来（GLM-01）。

**新方案：协商前置到发 OFFER 之前，走在线设备表。**

`OnlineDevice` 已经携带 `AppVersion`（`envelope.go:106`，客户端 `online_devices` 里有），
所以发送端在构造 OFFER 之前就知道对端版本：

```
发送端 cmd_send_files / cmd_send_clipboard
  → 查 online_devices 里目标设备的 app_version
  → 解析出是否 >= E2EE_MIN_VERSION
      是 ⇒ 构造加密 OFFER（元数据抹空并加密）
      否 ⇒ 构造明文 OFFER + 发出可见提示事件
```

这一条路径**单次 OFFER 即定形态**，不需要二次协商，因此：

- 不依赖 ANSWER 回传任何字段 ⇒ 绕开 GLM-01 的重建问题；
- 决策发生在抹空之前 ⇒ 解决 AGY-01/GLM-02 的时序矛盾；
- **仍然服务端零改动**（只读已有字段，不加新字段）。

`e2ee_version` 仍放进 OFFER（OFFER 路径确实原样透传，已复核），
但它的作用降级为**接收端的自描述**（告诉接收端这份 OFFER 是不是加密的），
不再承担协商职责。

**「已核验事实」表要改**：那一行拆成两行，分别写明 OFFER 与 ANSWER 两条转发路径的差异，
并注明 ANSWER 会被重建。这条差异本身值得写进代码注释——
它会绊倒任何下一个想给 ANSWER 加字段的人。

**新增的失败模式必须处理**：目标设备不在 `online_devices` 里（刚上线未同步、
设备表滞后）时 `app_version` 取不到。此时**按不支持处理**（保守回落明文 + 提示），
而不是乐观假设支持——后者会让接收端收到一份它解不开的 OFFER，
退回 AGY-01 的形态。

### 2.2 OFFER 元数据解密失败的拦截（对应 AGY-02）

在 `lib.rs` 的 `TRANSFER_OFFER` 分支**最前置**加一道解密关，顺序固定为：

```
收到 OFFER
  → offer.e2ee_version 存在？
      是 → 解密 encrypted_metadata
             成功 ⇒ 把明文字段还原进 offer 结构体，继续
             失败 ⇒ 回 TRANSFER_ANSWER(accepted=false,
                     reject_reason="E2EE_KEY_MISMATCH")，就地中止
      否 → 按明文 OFFER 走
  → 此后才 emit('transfer-offer-received') 与 record_task
```

两个要点写进注释：

- **解密必须先于 emit 与落库**，否则 UI 与数据库会拿到空文件名——
  而历史行一旦以空文件名落库，后续修剪与展示都会带着它；
- 这条路径让「PSK 不一致」在**信令阶段**就被发现并明确告知，
  而不是等到数据面 tag 失败。§2.4 的 tag 失败熔断因此退化为纯粹的防篡改兜底，
  两条机制职责不再重叠——这正是 AGY-02 指出的冲突。

### 2.3 AAD 与元数据 nonce 的完整规范（对应 AGY-03）

**AAD**：数据块与元数据**统一使用 `Aad::empty()`**。

理由写进注释（这是个需要解释的选择）：把帧头字段纳入 AAD 看似更严格，
但帧头里的 `item_index` / `chunk_index` **已经通过 nonce 参与了认证**——
改动它们会直接导致 nonce 不匹配、tag 校验失败。而 `total_chunks` / `flags`
被篡改的后果由上层逻辑兜住（块数不符会让传输无法完成）。
引入非空 AAD 会新增一处两端必须逐字节一致的约定，**失败形态是"能解密的数据解不开"**，
而收益是已经被 nonce 覆盖的那部分。选简单且可论证的一侧。

**元数据 nonce 完整定义**（补齐前 8 字节）：

```
nonce[0..4]  = 0x00000000
nonce[4..8]  = 0x00000000
nonce[8..12] = 0x00000001   （域分隔：1 = 元数据）
```

数据块的 `[8..12]` 恒为 `0x00000000`，两个域的 nonce 空间不相交。
元数据每个 session 只加密一次，所以前 8 字节恒零不产生复用。

**密文打包格式**也要写死：`ring` 的 `seal_in_place_append_tag` 产出
`ciphertext || tag`，整体 base64 后放进 `encrypted_metadata`。
接收端按 `len - GCM_TAG_LEN` 切分。这一条不写明，两端会各自约定。

### 2.4 tag 失败改为会话级熔断（对应 AGY-04）

原设计按 `(item_index, chunk_index)` 单块计数，阈值 3。滑动窗口为 4，
PSK 不一致时 4 个在途块**各自计数 1**，永远达不到 3 ⇒ 无限重传。

改为**双层**：

- 单块阈值 3（保留，处理极罕见的 CRC32 漏检后仍 tag 失败）；
- **会话级累计阈值 3**（新增，任意块的 tag 失败累加到同一个计数器）。

任一触顶即熔断整个会话，`TRANSFER_FAILURE` 带 `E2EE_AUTH_FAILED`。

会话级阈值同样取 3 的依据（ZCode 独立论证过并被我采纳）：CRC32 已算在密文上，
线路偶发损坏会先被 CRC32 拦下走 NACK，**能同时通过 CRC32 又 tag 失败的情形
实践中几乎只剩篡改或密钥不匹配**（CRC32 碰撞 2^-32 量级）。所以快速熔断不会误伤。

配套测试要覆盖**窗口并发**场景：构造 4 个在途块同时 tag 失败，
断言会话熔断而不是各自重传——这正是原设计会漏掉的形态。

### 2.5 §B 的同源清单补第四处：进度统计（对应 AGY-05 / GLM-05）

原清单三处（`total_chunks`、发送 offset、写盘 offset）漏了接收端进度累加
（`transfer_engine.rs:730`）。加密时它累加密文长度（含 tag），
而 `total_size` 是明文口径，发送端累加的又是明文长度——三方不一致。

清单改为**四处**，全部从 `plaintext_chunk_len(encrypted)` 取值，
接收端按**解密后的明文长度**累加。注释里点明「进度统计也必须按明文口径」。

测试补一条 `transferred_size` 不超过 `total_size` 的断言。
现有代码有 `.clamp(0.0, 100.0)`，**它会把这个 bug 盖住**——
所以断言要针对 `transferred_size` 本身，不能只看百分比。

### 2.6 续传相关三处改写为与现状一致（对应 GLM-03）

- **§C 情况 4** 改为：「续传尚未实现（`BitmapRepo` 无生产调用、`resumed_items` 恒空），
  当前每次重连都是新 session 新 key，天然安全。**若未来实现续传，
  不得复用 session_id 传不同内容**——这条必须写进续传自己的验收。」
- **§F 位图跨版本节**：保留为防御性设计，但注明「当前无生产写入路径」，
  免得下一个人以为它在生效。
- **验证第 5 步**改为：「断网重连后**从头重传**成功且 SHA256 通过」——
  顺带仍能覆盖 §B 的 offset 正确性，这是 ZCode 给的建议，比我原来的写法更可验证。

顺带记一条：`session_id` 的现铸点我在原稿里写的是 `prepare_offer` / `prepare_offer_from_bytes`，
ZCode 独立核实后指出实际在调用方 `clipboard_cmd.rs:278/310`，
`prepare_offer` 只是形参接收。**结论（不复用）成立，但我的定位不准**，
修订稿按实际位置写，`two_transfers_never_share_session_id` 守卫测试保留。

### 2.7 威胁模型补「防主动降级：达不成」（对应 GLM-04）

限制表新增一行：

| 达不成的 | 原因 |
| :--- | :--- |
| 防主动降级 | 协商信息（对端 app_version、OFFER 的 e2ee_version）全部经过服务器，恶意服务端可改写它们强制明文。**本轮是机会性加密，不是抗主动攻击的保证** |

回落提示的文案同步修正：不能写死「对端版本过旧」，因为**无法区分**
「对端确实老」与「协商被服务端剥离」。文案改为陈述现象 + 指明后果
（「本次传输未加密：未能确认对端支持加密」），并在文档里如实承认这两种原因不可区分。

`e2ee_enabled` 仍倾向默认 `true`（两侧都同意），但 ZCode 提的**严格模式**
（协商失败即拒绝发送，而不是回落）记为后续项——
它是把机会性加密变成保证的唯一途径，值得单独一轮。

### 2.8 §G 移出本轮（对应 AGY-06 / GLM-06）

`PSK 进 keychain` 整节移出，本轮聚焦数据面与信令面的载荷加密。

两条理由都采纳：Linux CI 无 D-Bus 的实际风险（AGY-06 给了具体的 workflow 行号），
以及「PSK 今天已用于 HMAC 鉴权，本轮不恶化存储层边界」——后者纠正了我原稿
把 §G 说成 §A「前置依赖」的拔高说法。**它是增强，不是前置。**

移交说明里必须带上 GLM-06 的未决策点：keyring 条目按 `account_id` 命名、
迁移时以当前 account_id 落条目、切账号读取失败要提示重输而**不得回落到上一个账号的 PSK**
（否则会出现「用 A 的 PSK 解 B 的会话」这类最难排查的故障）。

威胁模型里「防设备失窃：达不成」的那一行保持不变，并注明本轮不缓解。

### 2.9 §A 的 account_id 论证措辞修正（对应 GLM-07）

「UUIDv4 碰撞概率可忽略」那句是 session_id 的性质，错安到了 account_id 上。
改为如实表述：

> `account_id` 是用户自填标识（`[A-Za-z0-9._@-]`，1–64 字节，非 UUID）。
> 两端由服务端按账号隔离路由，能建立传输即保证两侧是同一个字符串，
> 故 info 绑定无需依赖其随机性。

设计不变，只改论证文字。

## 4. 两侧的独立价值与本轮方法论记录

**两个阻断项缺一不可。** 只修 AGY-01（把协商提前）而不知道 GLM-01，
我会把 `e2ee_ok` 从 ANSWER 挪到别处但仍相信「加字段能透传」；
只修 GLM-01（换通道）而不知道 AGY-01，我会把能力位塞进一个仍然太晚的时点。
两侧各自只看到一半，合起来才指向「协商必须前置且不能走 ANSWER」这个唯一解。

**ZCode 独立复核了我的重点提示第 1 条**（session_id 复用风险），
不仅确认结论成立，还纠正了我的定位错误（现铸点在调用方而非 `prepare_offer`）。
这正是重点提示该起的作用——它让审查员去验证我最不确定的地方，
而不是均匀地扫全文。

**Antigravity 在 §B 上给出了我没想到的连带影响**（AGY-05 的进度溢出），
ZCode 则把它归类为「§B 想防的同一类问题」。同一个事实，
前者发现、后者归类，合起来才让它落到正确的位置（同源清单）而不是被当成孤立小 bug。

**一条留给下一轮的方法论**：我这轮两处事实错误有同一个形状——
**核实了静态结构，没核实动态路径**（字段类型 vs 处理器行为；表结构 vs 是否有人写）。
下一轮写「已核验事实」表时，每一条都要问一句「我核的是声明还是行为」。

## 5. 验证（修订后）

计划阶段无代码改动，本节记录修订后的验收口径变更：

- 手工验证第 5 步改为「断网重连后从头重传成功且 SHA256 通过」（§2.6）；
- 新增手工验证：**新版发给旧版**时，发送端界面出现「未能确认对端支持加密」提示，
  且旧版接收端**传输成功**（因为发的是明文 OFFER，元数据未抹空）——
  这条直接验证 §2.1 是否真的修好了 AGY-01；
- 新增手工验证：两端 PSK 不同 ⇒ **在信令阶段**（不是数据面）就被拒绝，
  提示指向密钥不一致——验证 §2.2；
- 抓中继帧确认 payload 不可读且 OFFER 无明文文件名，这条保留，
  它仍是本轮唯一能直接证明目标达成的验证。
