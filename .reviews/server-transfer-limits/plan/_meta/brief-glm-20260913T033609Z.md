## 1. 背景与现状核验

### 1.1 需求原文

> 3. 服务端可以设置最大可以传输的文件或者剪贴板内容最大多大，当超出限制时，
>    客户端弹出提示：文件/剪贴板内容太大，无法传输。

一句话里有三个独立要件，缺一不可：**服务端可设置**、**超出时拒绝**、
**客户端弹出提示**。现状是三个都不满足（§1.2、§1.4）。

本轮是**首次改动 `server/`**。此前九轮需求全部落在 `client/`。

### 1.2 服务端现状：需求 3 要的限额根本不存在

全仓库现存的限制只有四处，**没有一处**限制单个文件大小或剪贴板内容大小：

| 限制 | 位置 | 值 | 可配置 | 超限行为 |
|---|---|---|---|---|
| 单次 offer 条目数 | `control_ws.go:255` | `1000`（裸字面量） | **否** | **静默丢弃** |
| 单帧 payload | `binary_header.go:23` | 4 MiB | 否 | 解码报错，切断数据面 |
| 并发管道总数 | `relay_manager.go:14` | 200（全局） | 否 | `ErrServerBusy` |
| 控制面单条消息 | `control_ws.go:46` | 512 KiB | 否 | websocket 库直接断连 |

四条里没有任何一条是按「文件大小」或「剪贴板内容大小」计的——
需求 3 要的那个维度目前在服务端完全不存在。

### 1.3 `config` 包里有两个死字段，`config.example.yaml` 整份不被读取

已逐个 grep 核实：

| 字段 | 定义 | 赋默认值 | 被读取 |
|---|---|---|---|
| `ListenAddr` | `config.go:11` | 是 | 是（`main.go:81`） |
| `PSKSecret` | `config.go:12` | 是 | 是（`main.go:31,35`） |
| `STUNAddr` | `config.go:12` | 是 | 是（`main.go:46`） |
| `HeartbeatTimeout` | `config.go:15` | 是 | 是（`main.go:61`） |
| **`MaxItemsPerOffer`** | `config.go:13` | 是（1000） | **否——死字段** |
| **`HeartbeatInterval`** | `config.go:14` | 是（15） | **否——死字段** |

`MaxItemsPerOffer` 与上一轮的 `DEFAULT_TTL` **完全同型**：配置项定义了、赋了值、
看起来是事实源，真正决定行为的却是 `control_ws.go:255` 的裸 `1000`。
改配置毫无效果，且没有任何编译警告（Go 的导出结构体字段不触发 unused 检查）。

更彻底的一点：**`server/configs/config.example.yaml` 整份都是装饰**。
`config.Load()` 只读环境变量，全 server 没有任何一行 YAML 解析代码
（`grep -rn "yaml\|ReadFile\|os.Open" --include='*.go'` 零命中）。
那份 example 里的 `max_items_per_offer`、`pipe_idle_timeout_seconds`、
`heartbeat_timeout_seconds`、甚至 `psk_secret` 与 `listen_addr`，**没有一个**
会被读取。照它配置服务器的人得到的是完全的静默无效。

**需求 3 的「服务端可以设置」让这条缺陷成为阻塞项**：env 是限额的唯一配置入口，
一份骗人的配置样例会直接导致「我明明配了上限，怎么没生效」。处置见 §6.2。

### 1.4 超限行为是静默丢弃——这正是需求 3 要修的缺陷

`control_ws.go:248-260`：

```go
case protocol.ActionTransferOffer:
    if env.ToDevice == "" { continue }
    var offer protocol.TransferOfferPayload
    if err := json.Unmarshal(env.Payload, &offer); err == nil {
        if len(offer.Items) > 1000 {
            slog.Warn("transfer offer exceeded items limit", ...)
            continue          // ← 发送方永远收不到任何回应
        }
    }
    h.routeToPeer(session, env)
```

此时发送端 `dispatch_offer`（`clipboard_cmd.rs:140-150`）**已经**把 offer 存进
`pending_outbound`、**已经**写了一行 `TRANSFERRING` 历史，然后永久等待一条
不会到来的 `TRANSFER_ANSWER`。卡片挂在「传输中」不动，一直到下次启动被
`reset_stale_in_flight` 复位成 FAILED——那可能是几天以后。

需求 3 的「客户端弹出提示」因此不只是加一句文案，而是要把这条静默通道
补成**显式拒绝**。

相邻缺陷：上面的 `if err == nil` 意味着 **payload 解析失败时反而放行**。
一个畸形 offer 绕过条目数检查直接被转发。本轮一并修正为解析失败即拒绝。

### 1.5 客户端现状：限额写死在发送端，且文件路径完全不检查

`clipboard_cmd.rs:16-17`：

```rust

const MAX_IMAGE_BYTES: usize = 32 * 1024 * 1024;  // 32 MB
```

- 这两个常量**只**在 `cmd_send_clipboard` 里被检查；
- **`cmd_send_files` 完全不检查大小**——选一个 100 GB 的文件也会照常算完
  SHA-256 再把 offer 发出去；
- 这两个值是客户端自己拍的，与服务端限额没有任何关系。需求 3 要求限额由
  **服务端**定义，因此本轮把它们降级为「服务端未下发时的兜底」。

### 1.6 `rate_limit_mb` 是第三个死字段

`settings_cmd.rs:12` 声明、默认 10、随设置落库，`types/index.ts:14` 也有类型。
但全仓库 grep 只命中声明、默认值构造与测试断言——**后端无一处读取，
`SettingsModal.tsx` 也根本没有渲染这个输入框**。用户看不见它，代码也不用它，
它唯一的作用是占着 JSON 里的一个键。

本仓库第三个同型陷阱（前两个：`DEFAULT_TTL`、`MaxItemsPerOffer`）。处置见 §6.3。

### 1.7 权限模型现状（本轮只作背景）

1. **整个部署共用一把 PSK**（`config.go:24`，`docker-compose.yml:16` 里还是明文）；
2. **`account_id` 由客户端自行声明**。它参与 HMAC 签名（`verifier.go:43-53`），
   但签名用的是那把**全局** PSK——所以任何知道 PSK 的客户端可以声明**任意**
   `account_id`。`registry` 按 `account_id` 做的隔离是**便利分区，不是安全边界**；
3. **服务端零持久化**：`config.Load()` 只读环境变量，`docker-compose.yml`
   **没有挂任何 volume**。

本轮不写任何服务端状态，因此第 3 条不构成约束。这三条在此记录，
是因为 `max_concurrent_transfers`（§4.1）按 `account_id` 计数——
其隔离强度受第 2 条限制，见 R5。

## 4. 协议与语义设计

### 4.1 限额集合（全部由服务端 env 配置）

| 字段 | 含义 | 默认值 | 精确字节数 | env 变量 |
|---|---|---|---|---|
| `max_single_file_bytes` | 单个文件字节上限 | 128 MB | `134_217_728` | `UNIDROP_MAX_SINGLE_FILE_BYTES` |
| `max_total_transfer_bytes` | 单次传输总字节上限 | 256 MB | `268_435_456` | `UNIDROP_MAX_TOTAL_TRANSFER_BYTES` |
| `max_clipboard_image_bytes` | 剪贴板图片（IMAGE）上限 | 64 MB | `67_108_864` | `UNIDROP_MAX_CLIPBOARD_IMAGE_BYTES` |
| `max_clipboard_text_bytes` | 剪贴板文本（TEXT）上限 | 4 MB | `4_194_304` | `UNIDROP_MAX_CLIPBOARD_TEXT_BYTES` |
| `max_items_per_offer` | 单次 offer 条目数 | 64 | — | `UNIDROP_MAX_ITEMS_PER_OFFER` |
| `max_concurrent_transfers` | **单账号**同时进行的传输数 | 8 | — | `UNIDROP_MAX_CONCURRENT_TRANSFERS` |

默认值由用户指定。前四项直接对应需求 3 的「文件」与「剪贴板内容」两个维度；
后两项是本轮顺带收敛的既有硬编码（§1.2、§6.1），不是需求 3 的要求，
但它们与前四项同属「服务端传输限额」这一个概念，分开做会造成第二套配置入口。

**剪贴板拆成图片、文本两项，是刻意的，不要再合并。** 需求 3 原文把它们
统称为「剪贴板内容」，看起来像一个概念，但两者的合理量级差一个数量级：
4 MB 文本约等于四百万字符（几乎不可能是真实剪贴内容，多半是误操作或程序输出），
而 4 MB 图片只是一张普通照片。用同一个数去卡，必然要么对文本过于宽松、
要么对图片过于苛刻。改造前客户端本就是两个常量（`MAX_TEXT_BYTES` /
`MAX_IMAGE_BYTES`），本轮保持这个划分。

**MB 一律按 1024×1024 计**（即口语的 MB、严格的 MiB）。这与本仓库既有约定一致
——`cache_max_size_mb` 就是标 MB、算 `* 1024 * 1024`。上表已钉死精确字节数，
实现与单测都以该数为准，不要在代码里再写一次 `128 * 1000 * 1000`。

### 4.1.1 两项行为变更，必须在验收中确认

新默认值**有松有紧**，其中两项会改变现有部署的可观察行为：

| 项 | 改造前实际生效 | 新默认 | 影响 |
|---|---|---|---|
| 单次 offer 条目数 | 1000（`control_ws.go:255` 裸字面量） | **64** | **约 15 倍收紧**。一次选 65 个及以上文件会被拒 |
| 剪贴板图片 | 32 MB（客户端 `MAX_IMAGE_BYTES`） | **64 MB** | **放宽一倍** |
| 剪贴板文本 | 4 MB（客户端 `MAX_TEXT_BYTES`） | 4 MB | 不变 |
| 单个文件大小 | 无任何限制 | 128 MB | 新增约束（`cmd_send_files` 改造前完全不检查，§1.5） |
| 单次传输总量 | 无任何限制 | 256 MB | 新增约束 |

后两行虽然不是「变更」而是「从无到有」，但对用户同样是新出现的拒绝，
验收时一并确认。

关于条目数：已核实 `prepare_offer`（`transfer_engine.rs:104-107`）遇到目录
**直接跳过、不递归展开**，所以 `items` 数就是用户手选的文件个数，一对一。
因此 `64` 的用户可见含义是「**一次最多选 64 个文件**」，不是「最多 64 层目录」
也不是「最多 64 个分片」。

条目数与总量哪条先触顶，取决于文件平均大小：

- 总量上限 256 MB ÷ 64 条 = **平均每个文件 4 MB**；
- 平均小于 4 MB 时，**先撞条目数**；大于 4 MB 时，先撞总量。

4 MB 这个分界点落得比较中庸：截图、文档一类会先撞条目数，
照片、短视频一类会先撞总量，两条限制都不会沦为摆设。
但这也意味着**两条超限文案都会被高频看到**，§4.4 的文案质量是实打实的
用户体验项，不是收尾装饰：`LIMIT_TOO_MANY_ITEMS` 必须写清「最多 64 个」、
`LIMIT_TOTAL_TOO_LARGE` 必须写清「总共不超过 256 MB」以及当前实际值，
而不是笼统说「文件太多」「内容太大」——用户看到具体数字才知道怎么调整，
看到形容词只能靠试。

关于剪贴板：改造前文本与图片就是**两个不同的常量**（4 MB / 32 MB），
本轮保持这个划分（理由见 §4.1）。文本的默认值与改造前完全一致，
图片放宽一倍。

> 顺带记录一个**本轮不修**的既有缺陷：`prepare_offer` 跳过目录时只打 warn
> 然后 `continue`。用户若同时选了一个目录和一个文件，目录会被**静默丢弃**，
> 只发出那个文件，而界面不会有任何提示。这是独立于需求 3 的缺陷，
> 修它要改「目录是否递归展开」的产品行为，超出本轮范围。记在此处避免
> 日后误以为是本轮引入的。

### 4.2 `0` 的语义与一个静默解除限制的陷阱

- **env 显式设为 `0`** = **不限制该项**。部署者有权关掉任何一项；
- **未设置该 env 变量** = 取上表默认值（**不是** 0）；
- **解析失败**（非数字、负数）= **取默认值并打 warn，不得静默变成 0**。

第三条是关键：`strconv.Atoi` 失败时返回的 `0` 恰好落在「不限制」上，
于是一个拼错的变量名、或者写成 `2GB` 这种带单位的值，会**静默解除**该项限制，
而部署者以为自己配了上限。现有 `config.go:38-41` 的写法
（`if err == nil && val > 0`）碰巧已经是对的形态，新增五项必须照抄它，
不得图省事简写成 `val, _ := strconv.Atoi(s)`。

本轮不存在客户端覆盖值，因此**没有第二套 `0` 语义**。
