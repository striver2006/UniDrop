## 2. 需要展开说明的裁决

### 2.1 AGY-01 / GLM-01：0 值语义与解析形态的自相矛盾（原稿最根本的错误）

原稿 §4.2 同时写了两句不可同真的话：

- 「env 显式设为 `0` = 不限制该项。部署者有权关掉任何一项」；
- 「现有 `config.go:38-41` 的写法（`err == nil && val > 0`）碰巧已经是对的形态，
  新增五项必须照抄它」。

`val > 0` 把 0 排除在外。照抄的结果是：部署者显式设 `UNIDROP_MAX_SINGLE_FILE_BYTES=0`
期望「不限制」，实际被当成无效值忽略、静默保持 128 MB 默认。
而 §7.1 我自己写的测试「该项设 0 时任意大小都通过」按被强制的形态实现**必然变红**。

GLM 点破了那个形态为什么在原处是对的：`HeartbeatTimeout` **没有**「0 = 不限制」
语义，所以对它而言 0 确实是非法值；五个新字段有这个语义，照搬就错。
我把「防误判」这个正确直觉，错误地具体化成了一个排除合法值的条件。

**修订后的三态规则**：

| 输入 | 结果 |
|---|---|
| 未设置该变量 | 取默认值 |
| 解析成功且 `val >= 0` | 原样采用（含 `0` = 不限制） |
| 解析失败，或 `val < 0` | 取默认值 + `slog.Warn` |

「未设置」与「显式设 0」必须可区分——这正是 `os.Getenv` 返回空串与返回 `"0"`
的区别，实现时不得先做 `if s == ""` 之外的归一化。

**AGY 额外提的溢出**一并接受：`strconv.Atoi` 返回 `int`，32 位平台上是 32 位，
而 `max_total_transfer_bytes` 默认 256 MB、部署者完全可能配到数 GB。
字节类字段统一用 `int64` + `strconv.ParseInt(s, 10, 64)`，条目数与并发数保持 `int`。

### 2.2 AGY-02：两侧冲突，判 AGY 对——原设计会制造本轮要消灭的那类陷阱

原稿 §4.4 写「剪贴板限额与文件限额同时适用，取更严的那条」，理由是
「部署者把图片上限调到 512 MB 时，单文件 128 MB 必须仍然拦得住」。

AGY 反对；GLM 在「认为正确」段背书了我的原设计。**我判 AGY 对**，三条理由：

**（1）它会让一个配置项配了不生效——正是本轮的主题。**
部署者把 `max_clipboard_image_bytes` 调到 512 MB，是在明确表达「允许大图」。
若 `max_single_file_bytes = 128 MB` 静默压制它，这个配置项就成了
**第四个「看起来是事实源、实际不生效」的东西**——前三个是 `DEFAULT_TTL`、
`MaxItemsPerOffer`、`rate_limit_mb`，本轮正是为清理它们而做。
在专门消灭该陷阱的一轮里新造一个，是自相矛盾。

**（2）错误码与文案会撒谎。** 200 MB 图片被 `max_single_file_bytes` 拦下，
回的是 `LIMIT_FILE_TOO_LARGE`、文案「文件太大」。而需求 3 的原文要求的是
**「文件/剪贴板内容太大」两种提示**——把剪贴板图片报成「文件」直接偏离需求原文。

**（3）GLM 的顾虑已被 `max_total_transfer_bytes` 覆盖。**
GLM 担心「图片上限调高时单文件维度仍须拦截」。但总量上限对**所有** `data_type`
适用：512 MB 图片在 `max_total_transfer_bytes = 256 MB` 下照样被拒，
且回的是 `LIMIT_TOTAL_TOO_LARGE`——**准确**的那条。
部署者要真发 512 MB 图片，必须把总量也调上去，这是可发现、可理解的。

**修订后的分层**：

| 维度 | 适用范围 | 字段 |
|---|---|---|
| 通用 | 所有 `data_type` | `max_total_transfer_bytes`、`max_items_per_offer` |
| 内容（按 `data_type` **互斥**） | `FILES` | `max_single_file_bytes` |
| | `IMAGE` | `max_clipboard_image_bytes` |
| | `TEXT` | `max_clipboard_text_bytes` |

互斥是关键词：走 IMAGE 分支就**不再**校验 `max_single_file_bytes`。

### 2.3 AGY-03 / GLM-03：预检时序——原稿只是把荒谬换了个位置

原稿 §1.5 把「选 100 GB 文件也会照常算完 SHA-256」列为现状荒谬之处，
然后 §4.5 把预检定在「`prepare_offer` 之后」——哈希照算，只是算完再拒。
GLM 的措辞准确：**「只是把荒谬从『发出去』改成『算完再拒』」**。

对需求 3 的「超出限制时客户端弹出提示」而言，几十 GB 文件等几分钟才弹提示，
接近于未实现。而文件大小只需 `fs::metadata` 即可知，根本不需要哈希。

更糟的是 GLM 复核出的一点（AGY 未察觉）：**剪贴板路径现状本就是哈希前检查**
（`clipboard_cmd.rs:185/191`，`MAX_TEXT_BYTES`/`MAX_IMAGE_BYTES` 在
`prepare_offer_from_bytes` 之前）。原稿的统一新时序会让它**倒退**。

**修订后的两级预检**：

- **第一级（metadata 级，进 `prepare_offer` 之前）**：逐文件
  `fs::metadata(p).len()` 校验单文件上限、累加校验总量、校验条目数。
  剪贴板 bytes 路径保持现状的哈希前检查；
- **第二级（`prepare_offer` 之后、`dispatch_offer` 之前）**：复核最终
  `items.len()` 与 `total_size`。

**第二级不是冗余，它防的是一个两侧都没提的假拒绝**：
`prepare_offer`（`transfer_engine.rs:104-113`）会**跳过目录与不可读文件**。
若第一级直接拿 `paths.len()` 去比条目数上限，用户选了 70 项、其中 10 项是目录时，
实际只会产生 60 个 item（未超 64），却在第一级被误拒。

因此**第一级的条目计数必须与 `prepare_offer` 的跳过逻辑口径一致**——
它本就要遍历 metadata 拿大小，在同一趟里过滤掉目录与不可读项即可，
不额外增加 IO。这一条写进计划，否则实现者按直觉写 `paths.len()` 必踩。

### 2.4 GLM-02：并发拒绝的回送对象——通过新路径复刻本轮要修的缺陷

这是 GLM 判定的最危险一条，AGY 未发现。已复核属实。

原稿 §4.4(4) 只写「超限回 `TRANSFER_FAILURE`」，没说回给谁、原 answer 是否转发。
按现有代码，两种自然实现都会让发送方永久挂起：

- **(a) 沿用现状**：`control_ws.go:289` 的 `h.routeToPeer(session, env)` 在
  `if` 块**之外**，authorize 失败后仍转发一条**无 token** 的 answer。
  客户端 `lib.rs:200-204` 的 `if let Some(token)` 不成立 → 整个分支静默跳过 →
  `pending_outbound` 永不消费；
- **(b) 丢弃 answer 只回接收方**：发送方永远等不到回应；且接收方在
  `lib.rs:185-194` **已经**写入了 `pending_inbound` 与 RECEIVE 方向的
  `TRANSFERRING` 历史行，同样无人复位。

两条路都是 §1.4 那个缺陷的翻版——在一轮专门修它的改动里，从新入口漏回来。

**修订后的契约**：拒绝时**不转发**原 answer；向**双方各发一条**
`TRANSFER_FAILURE`——接收方经 `session.Send`，发送方经该 answer 的 `ToDevice`
（对 ANSWER 而言 `ToDevice` 恰是发送方，此处 `routeToPeer` 的方向是对的，
与 OFFER 拒绝相反，实现时容易混淆，须在代码注释写明）。

**「在途」的计数口径**一并定死：= 该账号**已授权未终结**的会话，即
`authSessions`（而非 `pipes`——后者要双方都连上 `/ws/data` 才创建，
语义是「正在传数据」，会漏掉已授权但尚未连上的）。递减路径为
`RemovePipe` / `SweepIdlePipes` / 5 分钟 TTL 过期，三者已存在，无需新增。

这同时关闭原稿的 R4「统计位置未定」——与 AGY-06 的结论一致，
两侧从不同角度指向同一个归属：`RelayManager`。

### 2.5 AGY-05 / GLM-04：解析失败时的拒绝信是空头支票

原稿 §4.4(1) 要求 offer 解析失败即回 `TRANSFER_FAILURE`。但 payload 解不开，
`session_id` 也就取不到；而客户端 `lib.rs:255-269` 完全以 `payload.session_id`
为匹配键，`if let Some(sid)` 不成立时**什么也不做**。拒绝信发出去了，
落不到任何卡片上，该路径的挂起并未真正修复。

**修订后的契约（两段式）**：先用只含 `session_id` 的最小结构做一次宽松解析
（覆盖「JSON 结构合法但字段类型错」这一常见形态）；能提到就回带该 id 的失败信；
**连 `session_id` 都提不出来时，明确只能丢弃 + warn，并接受该极端路径挂起**。

最后半句是刻意写进计划的：让实现者知道这不是遗漏而是已知边界，
避免「回了信就完事」的错觉。完全无法解析的 payload 只可能来自非本项目客户端，
而那种对端的卡片状态本就不在我们的管辖内。

### 2.6 GLM-05：删字段「无迁移成本」只对升级方向成立

原稿 §6.3 写「serde 默认忽略未知字段，所以无迁移成本」——只说对了一半。

`rate_limit_mb`（`settings_cmd.rs:12`）**没有** `#[serde(default)]`。
新客户端保存的 JSON 不再含该键；用户一旦**回滚**到旧版本客户端，
旧结构体反序列化会整条失败，走 `lib.rs` 的 `unwrap_or_else` 静默回落全部默认值，
把 `server_url` / `account_id` / `psk_secret` 一起冲掉。

同一个文件 `settings_cmd.rs:15-18` 的注释正是这个事故的文档化记录——
我引用了那段注释去论证「加字段危险」，却没想到它对「删字段 + 回滚」同样成立。
方向反过来，机制一模一样。

**不改变删除决策**（GLM 亦明确「不必为此改变删除决策」），
但 §6.3 补上回滚风险说明。本项目发签名 dmg，版本回退是现实场景而非假想。

### 2.7 GLM-06：「服务端不能信客户端」说过头了

原稿 §4.5 末段写「服务端校验管正确性（客户端可以被改，服务端不能信客户端）」。

实际上服务端校验的对象是 offer 里客户端**自报**的 `size` / `total_size`
（`envelope.go:104-114`），数据面没有任何按会话聚合的字节核算
（`data_ws.go` 只有帧级 `ReadLimit` 与 `PayloadLen` 一致性）。
被改过的客户端可以申报 `total_size=1` 然后经管道流送任意多字节。

所以这组限额**只约束诚实客户端**，强度与 R5 对 `account_id` 的坦白定位相同。
原表述会让读者以为它对恶意客户端也可执行。

修订为：**限额是面向诚实客户端的容量与体验约束，不构成对篡改客户端的
字节级执行**；真正的执行需要管道级字节计数，明确不在本轮。§9 一并写入。

### 2.8 GLM-07：条目数与 512 KiB 信封上限的联动

`max_items_per_offer` 开放为 env 后，与 `control_ws.go:46` 的
`ws.SetReadLimit(512 * 1024)` 没有任何联动。部署者把它调大后，
超限 offer 不会走新建的拒绝路径，而是被 websocket 库**直接断连**——
静默挂起原样保留，且表现比条目数超限更迷惑（用户看到的是掉线，不是拒绝）。

粗估每条目 JSON 约 200–400 字节（`relative_path` + 64 字符 `sha256` + 数个整数，
且随文件名长度上不封顶），1000 条即可逼近 512 KiB。

落点：§4.1 补写该联动关系，`.env.example` 的注释给出保守建议上界，
并写入 §9 的需求文档说明——避免部署者调大后把断连误判成服务端 bug。
