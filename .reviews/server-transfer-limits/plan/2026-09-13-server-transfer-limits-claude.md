## 1. 背景与现状核验

### 1.1 需求原文

> 3. 服务端可以设置最大可以传输的文件或者剪贴板内容最大多大，当超出限制时，
>    客户端弹出提示：文件/剪贴板内容太大，无法传输。

一句话里有三个独立要件，缺一不可：**服务端可设置**、**超出时拒绝**、
**客户端弹出提示**。现状是三个都不满足（§1.2、§1.4）。

本轮是**首次改动 `server/`**。此前九轮需求全部落在 `client/`。

### 1.2 服务端现状：需求 3 要的限额根本不存在

全仓库现存的限制只有四处，**没有一处**限制单个文件大小或剪贴板内容大小：

| 限制 | 位置 | 值 | 可配置 | 超限行为 |
|---|---|---|---|---|
| 单次 offer 条目数 | `control_ws.go:255` | `1000`（裸字面量） | **否** | **静默丢弃** |
| 单帧 payload | `binary_header.go:23` | 4 MiB | 否 | 解码报错，切断数据面 |
| 并发管道总数 | `relay_manager.go:14` | 200（全局） | 否 | `ErrServerBusy` |
| 控制面单条消息 | `control_ws.go:46` | 512 KiB | 否 | websocket 库直接断连 |

四条里没有任何一条是按「文件大小」或「剪贴板内容大小」计的——
需求 3 要的那个维度目前在服务端完全不存在。

### 1.3 `config` 包里有两个死字段，`config.example.yaml` 整份不被读取

已逐个 grep 核实：

| 字段 | 定义 | 赋默认值 | 被读取 |
|---|---|---|---|
| `ListenAddr` | `config.go:11` | 是 | 是（`main.go:81`） |
| `PSKSecret` | `config.go:12` | 是 | 是（`main.go:31,35`） |
| `STUNAddr` | `config.go:12` | 是 | 是（`main.go:46`） |
| `HeartbeatTimeout` | `config.go:15` | 是 | 是（`main.go:61`） |
| **`MaxItemsPerOffer`** | `config.go:13` | 是（1000） | **否——死字段** |
| **`HeartbeatInterval`** | `config.go:14` | 是（15） | **否——死字段** |

`MaxItemsPerOffer` 与上一轮的 `DEFAULT_TTL` **完全同型**：配置项定义了、赋了值、
看起来是事实源，真正决定行为的却是 `control_ws.go:255` 的裸 `1000`。
改配置毫无效果，且没有任何编译警告（Go 的导出结构体字段不触发 unused 检查）。

更彻底的一点：**`server/configs/config.example.yaml` 整份都是装饰**。
`config.Load()` 只读环境变量，全 server 没有任何一行 YAML 解析代码
（`grep -rn "yaml\|ReadFile\|os.Open" --include='*.go'` 零命中）。
那份 example 里的 `max_items_per_offer`、`pipe_idle_timeout_seconds`、
`heartbeat_timeout_seconds`、甚至 `psk_secret` 与 `listen_addr`，**没有一个**
会被读取。照它配置服务器的人得到的是完全的静默无效。

**需求 3 的「服务端可以设置」让这条缺陷成为阻塞项**：env 是限额的唯一配置入口，
一份骗人的配置样例会直接导致「我明明配了上限，怎么没生效」。处置见 §6.2。

### 1.4 超限行为是静默丢弃——这正是需求 3 要修的缺陷

`control_ws.go:248-260`：

```go
case protocol.ActionTransferOffer:
    if env.ToDevice == "" { continue }
    var offer protocol.TransferOfferPayload
    if err := json.Unmarshal(env.Payload, &offer); err == nil {
        if len(offer.Items) > 1000 {
            slog.Warn("transfer offer exceeded items limit", ...)
            continue          // ← 发送方永远收不到任何回应
        }
    }
    h.routeToPeer(session, env)
```

此时发送端 `dispatch_offer`（`clipboard_cmd.rs:140-150`）**已经**把 offer 存进
`pending_outbound`、**已经**写了一行 `TRANSFERRING` 历史，然后永久等待一条
不会到来的 `TRANSFER_ANSWER`。卡片挂在「传输中」不动，一直到下次启动被
`reset_stale_in_flight` 复位成 FAILED——那可能是几天以后。

需求 3 的「客户端弹出提示」因此不只是加一句文案，而是要把这条静默通道
补成**显式拒绝**。

相邻缺陷：上面的 `if err == nil` 意味着 **payload 解析失败时反而放行**。
一个畸形 offer 绕过条目数检查直接被转发。本轮一并修正为解析失败即拒绝。

### 1.5 客户端现状：限额写死在发送端，且文件路径完全不检查

`clipboard_cmd.rs:16-17`：

```rust
const MAX_TEXT_BYTES: usize = 4 * 1024 * 1024;    // 4 MB
const MAX_IMAGE_BYTES: usize = 32 * 1024 * 1024;  // 32 MB
```

- 这两个常量**只**在 `cmd_send_clipboard` 里被检查；
- **`cmd_send_files` 完全不检查大小**——选一个 100 GB 的文件也会照常算完
  SHA-256 再把 offer 发出去；
- 这两个值是客户端自己拍的，与服务端限额没有任何关系。需求 3 要求限额由
  **服务端**定义，因此本轮把它们降级为「服务端未下发时的兜底」。

### 1.6 `rate_limit_mb` 是第三个死字段

`settings_cmd.rs:12` 声明、默认 10、随设置落库，`types/index.ts:14` 也有类型。
但全仓库 grep 只命中声明、默认值构造与测试断言——**后端无一处读取，
`SettingsModal.tsx` 也根本没有渲染这个输入框**。用户看不见它，代码也不用它，
它唯一的作用是占着 JSON 里的一个键。

本仓库第三个同型陷阱（前两个：`DEFAULT_TTL`、`MaxItemsPerOffer`）。处置见 §6.3。

### 1.7 权限模型现状（本轮只作背景）

1. **整个部署共用一把 PSK**（`config.go:24`，`docker-compose.yml:16` 里还是明文）；
2. **`account_id` 由客户端自行声明**。它参与 HMAC 签名（`verifier.go:43-53`），
   但签名用的是那把**全局** PSK——所以任何知道 PSK 的客户端可以声明**任意**
   `account_id`。`registry` 按 `account_id` 做的隔离是**便利分区，不是安全边界**；
3. **服务端零持久化**：`config.Load()` 只读环境变量，`docker-compose.yml`
   **没有挂任何 volume**。

本轮不写任何服务端状态，因此第 3 条不构成约束。这三条在此记录，
是因为 `max_concurrent_transfers`（§4.1）按 `account_id` 计数——
其隔离强度受第 2 条限制，见 R5。

## 2. 交付目标

**服务端拥有一组 env 配置的限额、在 `TRANSFER_OFFER` 与 `TRANSFER_ANSWER` 上执行、
超限时回 `TRANSFER_FAILURE`；限额在鉴权成功后下发给客户端，客户端在发送前本地
预检并内联提示，同时在设置面板只读展示。**

## 3. 已删除的第 6 条：权限模型论证存档

第 6 条曾要求「客户端可以设置服务端的一些参数」。当时论证了三个方案，
用户选定 A 之后又删除了整条需求。**本轮不实现任何写回路径**，
以下仅为存档，避免日后重提时重新推导。

### 3.1 方案 A（曾选定）：只读下发

服务端限额只由 env 决定，鉴权后下发给客户端只读展示。
零新增攻击面、零服务端持久化、实现面最小；代价是改限额必须登服务器改 env 重启。

**本轮的 §4–§5 就是方案 A 的形态**——需求 3 本身只要求「服务端可以设置」，
这与方案 A 完全重合。所以第 6 条的删除并不减少本轮的工作量，只是去掉了
一个本来就没打算做的写回通道。

### 3.2 方案 B（曾驳回）：管理员凭证 + 全局可写

新增 `UNIDROP_ADMIN_TOKEN`，持有者可改写全局限额。驳回理由：给一个目前
零持久化、零凭证分级的服务端同时引入第二套凭证和持久化需求；且「管理员」
在单 PSK 模型里无法与普通用户真正区分——知道 PSK 的人离拿到 ADMIN_TOKEN
只差一次配置泄漏，两者通常写在同一个 `.env` 里。

### 3.3 方案 C（曾驳回）：按账号可写 + 服务端持有硬上限

各账号可在 env 硬上限之内调低自己的限额，覆盖值存服务端内存、
由客户端每次重连补发（服务端无需持久化）。攻击面论证成立
（知道 PSK 者本来就能冒充任意账号），但引入按账号分桶的内存态、钳制函数、
写回 action、重连补发机制，以及一个已知代价：服务端重启后到客户端重连前，
覆盖值有一段窗口不生效。

### 3.4 将来若要开写回，本轮已经铺好的地基

`ServerLimits` 结构、`AUTH_RESPONSE` 下发通道、客户端的 limits 状态与前端呈现
**全部可复用**。届时只需新增：一条写回 action、一个钳制纯函数、一套权限判定。

**本轮不预留任何「为将来准备」的空壳代码**——空壳本身就是下一个
`MaxItemsPerOffer`。第 6 条既已删除，预留就更无依据。

## 4. 协议与语义设计

### 4.1 限额集合（全部由服务端 env 配置）

| 字段 | 含义 | 默认值 | 精确字节数 | env 变量 |
|---|---|---|---|---|
| `max_single_file_bytes` | 单个文件字节上限 | 128 MB | `134_217_728` | `UNIDROP_MAX_SINGLE_FILE_BYTES` |
| `max_total_transfer_bytes` | 单次传输总字节上限 | 256 MB | `268_435_456` | `UNIDROP_MAX_TOTAL_TRANSFER_BYTES` |
| `max_clipboard_image_bytes` | 剪贴板图片（IMAGE）上限 | 64 MB | `67_108_864` | `UNIDROP_MAX_CLIPBOARD_IMAGE_BYTES` |
| `max_clipboard_text_bytes` | 剪贴板文本（TEXT）上限 | 4 MB | `4_194_304` | `UNIDROP_MAX_CLIPBOARD_TEXT_BYTES` |
| `max_items_per_offer` | 单次 offer 条目数 | 64 | — | `UNIDROP_MAX_ITEMS_PER_OFFER` |
| `max_concurrent_transfers` | **单账号**同时进行的传输数 | 8 | — | `UNIDROP_MAX_CONCURRENT_TRANSFERS` |

默认值由用户指定。前四项直接对应需求 3 的「文件」与「剪贴板内容」两个维度；
后两项是本轮顺带收敛的既有硬编码（§1.2、§6.1），不是需求 3 的要求，
但它们与前四项同属「服务端传输限额」这一个概念，分开做会造成第二套配置入口。

**剪贴板拆成图片、文本两项，是刻意的，不要再合并。** 需求 3 原文把它们
统称为「剪贴板内容」，看起来像一个概念，但两者的合理量级差一个数量级：
4 MB 文本约等于四百万字符（几乎不可能是真实剪贴内容，多半是误操作或程序输出），
而 4 MB 图片只是一张普通照片。用同一个数去卡，必然要么对文本过于宽松、
要么对图片过于苛刻。改造前客户端本就是两个常量（`MAX_TEXT_BYTES` /
`MAX_IMAGE_BYTES`），本轮保持这个划分。

**MB 一律按 1024×1024 计**（即口语的 MB、严格的 MiB）。这与本仓库既有约定一致
——`cache_max_size_mb` 就是标 MB、算 `* 1024 * 1024`。上表已钉死精确字节数，
实现与单测都以该数为准，不要在代码里再写一次 `128 * 1000 * 1000`。

### 4.1.1 两项行为变更，必须在验收中确认

新默认值**有松有紧**，其中两项会改变现有部署的可观察行为：

| 项 | 改造前实际生效 | 新默认 | 影响 |
|---|---|---|---|
| 单次 offer 条目数 | 1000（`control_ws.go:255` 裸字面量） | **64** | **约 15 倍收紧**。一次选 65 个及以上文件会被拒 |
| 剪贴板图片 | 32 MB（客户端 `MAX_IMAGE_BYTES`） | **64 MB** | **放宽一倍** |
| 剪贴板文本 | 4 MB（客户端 `MAX_TEXT_BYTES`） | 4 MB | 不变 |
| 单个文件大小 | 无任何限制 | 128 MB | 新增约束（`cmd_send_files` 改造前完全不检查，§1.5） |
| 单次传输总量 | 无任何限制 | 256 MB | 新增约束 |

后两行虽然不是「变更」而是「从无到有」，但对用户同样是新出现的拒绝，
验收时一并确认。

关于条目数：已核实 `prepare_offer`（`transfer_engine.rs:104-107`）遇到目录
**直接跳过、不递归展开**，所以 `items` 数就是用户手选的文件个数，一对一。
因此 `64` 的用户可见含义是「**一次最多选 64 个文件**」，不是「最多 64 层目录」
也不是「最多 64 个分片」。

条目数与总量哪条先触顶，取决于文件平均大小：

- 总量上限 256 MB ÷ 64 条 = **平均每个文件 4 MB**；
- 平均小于 4 MB 时，**先撞条目数**；大于 4 MB 时，先撞总量。

4 MB 这个分界点落得比较中庸：截图、文档一类会先撞条目数，
照片、短视频一类会先撞总量，两条限制都不会沦为摆设。
但这也意味着**两条超限文案都会被高频看到**，§4.4 的文案质量是实打实的
用户体验项，不是收尾装饰：`LIMIT_TOO_MANY_ITEMS` 必须写清「最多 64 个」、
`LIMIT_TOTAL_TOO_LARGE` 必须写清「总共不超过 256 MB」以及当前实际值，
而不是笼统说「文件太多」「内容太大」——用户看到具体数字才知道怎么调整，
看到形容词只能靠试。

关于剪贴板：改造前文本与图片就是**两个不同的常量**（4 MB / 32 MB），
本轮保持这个划分（理由见 §4.1）。文本的默认值与改造前完全一致，
图片放宽一倍。

> 顺带记录一个**本轮不修**的既有缺陷：`prepare_offer` 跳过目录时只打 warn
> 然后 `continue`。用户若同时选了一个目录和一个文件，目录会被**静默丢弃**，
> 只发出那个文件，而界面不会有任何提示。这是独立于需求 3 的缺陷，
> 修它要改「目录是否递归展开」的产品行为，超出本轮范围。记在此处避免
> 日后误以为是本轮引入的。

### 4.2 `0` 的语义与一个静默解除限制的陷阱

- **env 显式设为 `0`** = **不限制该项**。部署者有权关掉任何一项；
- **未设置该 env 变量** = 取上表默认值（**不是** 0）；
- **解析失败**（非数字、负数）= **取默认值并打 warn，不得静默变成 0**。

第三条是关键：`strconv.Atoi` 失败时返回的 `0` 恰好落在「不限制」上，
于是一个拼错的变量名、或者写成 `2GB` 这种带单位的值，会**静默解除**该项限制，
而部署者以为自己配了上限。现有 `config.go:38-41` 的写法
（`if err == nil && val > 0`）碰巧已经是对的形态，新增五项必须照抄它，
不得图省事简写成 `val, _ := strconv.Atoi(s)`。

本轮不存在客户端覆盖值，因此**没有第二套 `0` 语义**。

### 4.3 下发：扩展 `AUTH_RESPONSE`

在 `AuthResponsePayload` 增加 `limits` 字段（`*ServerLimits`，`omitempty`）。

- **为什么挂在 AUTH_RESPONSE**：鉴权成功是客户端能拿到服务端策略的最早时点，
  不需要新增 action，也不需要客户端主动问一次；
- **新服务端 → 旧客户端**：Rust 侧 serde 默认忽略未知字段，无害；
- **旧服务端 → 新客户端**：`limits` 缺失。客户端必须声明成
  `Option<ServerLimits>`，**`None` 时退回「不做本地预检、沿用 §1.5 的兜底常量」，
  而不是退回「无限制」也不是「全部归零」**。这三种行为在代码里只差一个
  `unwrap_or_default()`，但后果分别是：一切照旧 / 老服务器上限额全失效 /
  老服务器上什么都发不出去。

#### 4.3.1 兜底常量取值：保持 4 MB / 32 MB 不变，**不要与服务端默认值共用常量**

`limits` 为 `None` 只在一种情况下出现：**对端是旧服务端**。那台服务端上
本来就没有任何限额，客户端这两个常量是当时唯一生效的约束。
因此兜底值必须**原样保留** `MAX_TEXT_BYTES = 4 MB`、`MAX_IMAGE_BYTES = 32 MB`。

图片那条容易看出来：兜底 32 MB ≠ 服务端默认 64 MB。若跟着改成 64 MB，
等于**在一台没装本轮改动的旧服务端上单方面放宽了限制**——旧服务端不会拒绝，
于是 50 MB 的图片真的会被发出去，而它此前是被客户端拦住的。
这是升级引入的行为变化，不是限额生效。

**文本那条是个更阴的陷阱：兜底 4 MB 与服务端默认 4 MB 恰好相等。**
两个数值相同，会强烈诱使实现者把它们合并成同一个常量。**不要合并**——
它们相等是**巧合**，不是同一件事：

- 兜底值表达的是「旧环境里的原样」，它的正确性依据是改造前的
  `MAX_TEXT_BYTES`，只有在需要故意改变旧环境行为时才该动；
- 服务端默认值表达的是「新策略」，部署者随时可能调整，
  将来某一轮也可能改成别的数。

共用一个常量的后果是：将来有人把服务端默认文本上限从 4 MB 调到 8 MB，
兜底值会被**静默拖着一起变**，旧服务端上的行为随之漂移，
而改动者完全不知道自己动了第二样东西。

实现时两处必须是各自独立的常量，并在注释里写明「数值相同是巧合，不得合并」。
§7.2 有一条专门的测试把这两个数分别钉死。

### 4.4 执行：`TRANSFER_OFFER` 校验 + 显式拒绝

改写 `control_ws.go` 的 `ActionTransferOffer` 分支：

1. 解析失败 → **拒绝**（修正 §1.4 的放行缺陷），回 `TRANSFER_FAILURE`；
2. 逐项校验：条目数、总字节、单文件最大字节（遍历 `offer.Items` 取 max）；
   `data_type` 为 `IMAGE` 时另按 `max_clipboard_image_bytes`、为 `TEXT` 时
   另按 `max_clipboard_text_bytes` 校验。**剪贴板限额与文件限额同时适用，
   取更严的那条**——图片默认 64 MB 低于单文件 128 MB，今天不会冲突，
   但部署者把图片上限调到 512 MB 时，单文件 128 MB 必须仍然拦得住，
   不能因为走了剪贴板分支就跳过文件维度的校验；
3. 任一超限 → **不转发**，向**发送方**回一条 `TRANSFER_FAILURE`：
   - `error_code`：按超限项区分——`LIMIT_FILE_TOO_LARGE` /
     `LIMIT_TOTAL_TOO_LARGE` / `LIMIT_IMAGE_TOO_LARGE` / `LIMIT_TEXT_TOO_LARGE` /
     `LIMIT_TOO_MANY_ITEMS`
   - `error_message`：中文可读文案，含实际值与上限值
4. 并发数校验挂在 `TRANSFER_ANSWER` 授权处（`AuthorizeSession` 之前统计该账号
   在途会话数），超限回 `TRANSFER_FAILURE`。

**拒绝信的回送方向容易写反**：现成的 `routeToPeer` 是发给 `env.ToDevice` 的，
而拒绝信要发回 `session` 自己。顺手复用 `routeToPeer` 会把「你的文件太大」
发给接收方，发送方那边依旧静默挂起——缺陷原封不动地保留下来。

客户端 `lib.rs:255-302` 的 `TRANSFER_FAILURE` 分支**已经**会把卡片翻红并把
`error_message` 拼进 summary，无需改动即可展示。

### 4.5 本地预检：客户端在发送前就拦（需求 3「弹出提示」的落点）

`cmd_send_files` / `cmd_send_clipboard` 在 `prepare_offer` 之后、`dispatch_offer`
之前按下发的 limits 校验，超限直接返回 `Err("…太大，无法传输…")`。

`SendModal.tsx:178-182` 已有 `errorMsg` 内联展示，需求 3 的提示天然落地，
不需要新增 UI。**注意 `SendModal.tsx:181` 有 `truncate`**——文案必须短，
长句会被 CSS 截断，用户看不到关键的数字。

**服务端拒绝（§4.4）是兜底，不是主路径**：offer 发出时 SendModal 已经关了，
那条路径只能把卡片翻红，给不出需求 3 要的「弹出提示」体验。两条都要有——
本地预检管体验，服务端校验管正确性（客户端可以被改，服务端不能信客户端）。

### 4.6 呈现：设置面板只读展示

`SettingsModal` 新增「服务端限额」分区，**纯展示，无输入框**，
并明确写出「由服务端配置，如需调整请联系部署者」——
避免用户对着一组灰色数字猜为什么改不了。

未连接或旧服务端（`limits` 为 `None`）时显示「未下发（服务端版本较旧）」，
不显示 0，也不显示默认值——显示默认值会让用户以为那就是生效值。

## 6. 需要一并收敛的既有缺陷

### 6.1 `config.MaxItemsPerOffer` / `HeartbeatInterval` 两个死字段

本轮新增五个限额字段到同一个结构体里。若把死字段留着，下一个读这段代码的人
无法分辨哪些是活的——这正是 `DEFAULT_TTL` 当初骗到人的机制。
`MaxItemsPerOffer` 恰好被本轮的 `max_items_per_offer` 取代；
`HeartbeatInterval` 没有对应物，直接删（心跳间隔由客户端决定，
服务端只用 Timeout 扫描）。

### 6.2 `config.example.yaml` 整份不被读取

需求 3 的「服务端可以设置」使 env 成为限额的唯一入口，这份骗人的样例会直接
导致「我明明配了上限，怎么没生效」。两条路：（a）真的实现 YAML 解析；
（b）改成与实际机制一致的 `.env.example`。

**倾向 (b)**：`Load()` 是 env-only 的设计，`docker-compose.yml` 也走 env，
实现 YAML 解析属于本轮范围外的新功能。改成 `.env.example` 是把文档改成事实，
成本最低且立刻消除误导；客户端侧已有 `.env.example` 的先例可对齐。

### 6.3 `rate_limit_mb` 死字段

**删除，不复用。** 它的名字是「速率限制 MB」（带宽语义），而需求 3 要的是
「单个文件大小上限」（体积语义）。复用会制造第二重误导——一个叫 rate_limit 的
字段实际控制的是 file size。

删除后老库 JSON 里仍有这个键：serde 默认**忽略**未知字段，所以无迁移成本。
（这与「新增字段必须有自定义 default」是两个方向，不要混淆——删字段安全，
加字段危险。）

### 6.4 `TRANSFER_OFFER` 解析失败时反而放行

见 §1.4 末段，随 §4.4 一并修正。

### 6.5 需求条目重编号的连带影响

第 6 条被删除后，旧 7/8/9/10 顺延为新 6/7/8/9。已 grep 全仓库，
**业务代码里有两处注释指向了错误的条目**：

- `client/src-tauri/src/core/cache_manager.rs:477` — 「需求 9」应为「需求 8」
- `client/src/components/SettingsModal.test.tsx:126` — 「需求 9」应为「需求 8」

需求 4、5 的引用不受影响（编号未变）。

**`.reviews/` 下的历史留痕一律不动**：那些文档记录的是各轮审查当时的事实，
按新编号回改等于伪造留痕。日后对账时以留痕的日期与主题名为准，不以条目号为准。

## 7. 测试计划

### 7.1 服务端单测（Go，新增）

- `Check()` 各项边界：**恰好等于上限必须通过**，上限 +1 必须拒绝；
- `0 = 不限制`：该项设 0 时任意大小都通过；
- env 解析：未设置取默认值；设非法值（负数、非数字、带单位如 `2GB`）
  **取默认值并 warn，不得变成 0**——守护 §4.2 那个静默解除限制的陷阱；
- 多项同时超限时 `error_code` 的选取是确定的（不依赖 map 遍历顺序）；
- `control_ws` 集成测：超限 offer 必须收到 `TRANSFER_FAILURE`、
  **该失败必须到达发送方**、且 offer **不被转发**给对端
  （现有 `control_ws_test.go` 已有握手脚手架可复用）；
- 畸形 payload 必须被拒绝而不是放行；
- 并发数统计的 `go test -race`。

### 7.2 客户端单测（Rust）

- `limits` 为 `None`（旧服务端）时沿用兜底常量，**不退化成零上限、
  也不退化成无限制**——§4.3 那三选一；
- 兜底常量的**具体数值**分别钉死为文本 4 MB、图片 32 MB。把图片兜底跟着
  服务端默认改成 64 MB，或把文本兜底与服务端默认文本上限合并成同一个常量，
  这条测试都必须变红（§4.3.1 的唯一自动化守护——否则「顺手统一」是无声的，
  尤其文本那两个数恰好相等，肉眼审查几乎发现不了）；
- 预检在 `prepare_offer` 之后、`dispatch_offer` 之前：超限时**不得**留下
  `pending_outbound` 条目与 `TRANSFERRING` 历史行（否则又制造一个
  §1.4 那样的永久挂起卡片）；
- 老库 JSON（含已删除的 `rate_limit_mb`、不含新字段）能正常反序列化且不丢配置。

### 7.3 前端单测（vitest）

- `limits` 为 null 时显示「未下发」而非 0 或默认值；
- 只读分区不产生可提交的表单字段（不污染 `cmd_save_settings` 的 payload）。

### 7.4 端到端手工验收（**必须人工执行，自动化测不到**）

1. 发一个超过 `max_single_file_bytes` 的文件 → SendModal 内联报「文件太大，
   无法传输」，且**没有**产生历史记录与传输卡片；
2. 发一张超过 `max_clipboard_image_bytes` 的图片、一段超过
   `max_clipboard_text_bytes` 的文本 → 同上，且两者的提示文案要能区分；
3. 把服务端 env 调小后重启 → 客户端重连 → 面板显示的是新值；
4. 篡改/绕过客户端预检（直接构造超限 offer）→ 服务端必须拒绝并回
   `TRANSFER_FAILURE`，**发送方**卡片翻红且能看到原因；
5. **版本交叉**：旧客户端连新服务端、新客户端连旧服务端，两个方向都不得崩溃、
   不得退化成无限制；
6. 设置面板新增分区后，380×560 窗口内滚动正常、底部按钮可达（上一轮的回归点）；
7. **行为变更逐项确认**（§4.1.1）：选 65 个文件被拒；发 50 MB 图片可以发出
   （改造前被 32 MB 兜底拦住）；发 4 MB 以上文本被拒（与改造前一致）；
   发 150 MB 单文件被拒、发总量 300 MB 被拒（改造前两者都完全不检查）。
   这些都是**有意的**默认值变更，验收目的是确认符合预期，而不是发现 bug。
   请特别看**文案**：条目数与总量两条会被高频触发，提示里必须分别出现
   「64」与「256 MB」这两个具体数字以及当前实际值，用户才知道怎么调整。

> 前九轮需求的端到端验收**至今一次都没有真正跑过**，两侧审查员每轮都把这列为盲区。
> 本轮涉及首次改动服务端与协议兼容性，第 4、5 项无法靠单测覆盖。
